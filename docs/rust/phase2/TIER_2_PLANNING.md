# Phase 2 Tier 2: Complex C++ FFI Migration Planning

**Status**: Planning / Strategy Document  
**Date**: 2026-01-01  
**Phase**: Phase 2 Tier 2 - Complex C++ FFI Components

---

## Overview

Phase 2 Tier 2 focuses on migrating Rust components that have **complex C++ FFI integration** and deep dependencies on Chromium's C++ infrastructure. These components are more challenging than Tier 1 because they depend on:

1. Chromium base library (//base)
2. GN-generated header files (buildflags, config headers)
3. Complex dependency chains across multiple C++ libraries
4. Platform-specific build configuration

## Tier 1 vs Tier 2 Distinction

### Tier 1 Components (✅ Complete)
- **Characteristics**:
  - Pure Rust or minimal C++ FFI
  - Self-contained or depends only on external crates
  - Can build with Cargo alone (no GN required)
  - Simple cxx bridge integration

- **Examples**:
  - `testing/rust_gtest_interop` - Test infrastructure
  - `tools/crates/gnrt` - Build tools
  - `components/qr_code_generator` - Minimal FFI, no base deps
  - `components/facilitated_payments/core/validation` - Simple validation logic
  - `components/user_data_importer/utility/parsing_ffi` - File parsing
  - `media/filters` - Symphonia integration

### Tier 2 Components (📋 Planning)
- **Characteristics**:
  - Complex C++ FFI with multiple integration points
  - Depends on Chromium base library (//base)
  - Requires GN-generated headers
  - Deeper integration with Chromium infrastructure
  - May require hybrid GN+Cargo build

- **Candidate Examples**:
  - `device/bluetooth/bluez/ble_scan_parser` - Bluetooth parser with base deps
  - `ui/android/texture_compressor` - Graphics with SIMD, requires nightly Rust
  - Additional media components with complex codec integration
  - Network utilities with platform-specific code

## Key Challenges

### 1. GN-Generated Headers

Many Chromium components depend on build-time generated headers:

```cpp
#include "base/debug/debugging_buildflags.h"  // Generated by GN
#include "build/build_config.h"                 // Generated by GN
```

**Problem**: Cargo doesn't know how to generate these headers.

**Solutions**:
- **Option A**: Hybrid Build - Require GN to run first, then Cargo uses generated headers
- **Option B**: Header Stubs - Create minimal stub headers for Cargo-only builds (limited scope)
- **Option C**: Code Generation - Reimplement header generation in Cargo build scripts (complex)

### 2. Chromium Base Library Dependencies

The Chromium `//base` library is fundamental infrastructure but has:
- Extensive use of GN build configuration
- Platform-specific implementations
- Complex dependency graph
- Not designed for Cargo integration

**Problem**: Components depending on //base can't easily build standalone with Cargo.

**Solutions**:
- **Option A**: Hybrid Build - Use GN to build //base, link from Cargo
- **Option B**: Base Subset - Create Cargo-compatible subset of //base (major effort)
- **Option C**: Abstraction Layer - Create FFI boundary that doesn't require base headers

### 3. Platform-Specific Build Configuration

Chromium uses GN for sophisticated platform targeting:
```python
if (is_chromeos) {
  sources += ["chromeos_specific.cc"]
}
```

**Problem**: Cargo's cfg system doesn't map 1:1 to GN's platform model.

**Solutions**:
- **Option A**: Feature Flags - Use Cargo features to approximate GN targets
- **Option B**: Build Scripts - Use build.rs to detect platform and configure appropriately
- **Option C**: Accept Limitations - Some components may not be fully portable via Cargo

## Proposed Migration Strategies

### Strategy 1: Hybrid GN+Cargo Build (Recommended for Tier 2)

This approach acknowledges that some components are deeply integrated with Chromium's build system.

**Process**:
1. Run GN to generate headers and build C++ dependencies
2. Use Cargo to build Rust code, linking against GN outputs
3. Integrate into workspace with appropriate documentation

**Advantages**:
- Realistic for complex components
- Maintains compatibility with existing infrastructure
- Incremental path forward
- Doesn't require rewriting C++ infrastructure

**Disadvantages**:
- Requires GN to be run first
- Not pure Cargo build
- More complex developer workflow

**Implementation**:
```toml
# Cargo.toml
[package]
name = "complex-component"
build = "build.rs"

[dependencies]
cxx = "1.0"

[build-dependencies]
cxx-build = "1.0"
```

```rust
// build.rs
fn main() {
    // Check for GN build outputs
    let out_dir = PathBuf::from("../../out/Default");
    if !out_dir.exists() {
        eprintln!("ERROR: GN build required before Cargo build");
        eprintln!("Run: gn gen out/Default && ninja -C out/Default");
        std::process::exit(1);
    }
    
    cxx_build::bridge("src/ffi.rs")
        .include("../..")  // Chromium root
        .include(out_dir.join("gen"))  // GN-generated headers
        .file("src/wrapper.cc")
        .compile("component_cxx");
}
```

**Documentation Required**:
- Clear README explaining build requirements
- Script to run GN then Cargo
- CI/CD integration instructions

### Strategy 2: Abstraction Layer for Base Dependencies

Create a thin FFI layer that minimizes direct base dependencies.

**Process**:
1. Identify minimal base APIs actually needed
2. Create C++ wrapper functions that don't expose base types
3. Use basic C types across FFI boundary
4. Implement Rust-side equivalents where possible

**Example**:
```cpp
// Instead of exposing base::span directly
void ProcessData(const base::span<const uint8_t>& data) { ... }

// Create wrapper with basic C types
void ProcessDataFFI(const uint8_t* data, size_t len) {
    ProcessData(base::span(data, len));
}
```

**Advantages**:
- Reduces dependency on GN-generated headers
- More Cargo-friendly
- Better separation of concerns

**Disadvantages**:
- Requires refactoring existing code
- Additional FFI layer overhead
- May not be practical for all components

### Strategy 3: Deferred Migration

Some Tier 2 components may not be worth migrating to Cargo yet.

**Criteria for Deferral**:
- Very deep integration with C++ infrastructure
- Low benefit from Cargo migration
- Active development in progress (avoid churn)
- Planned for eventual Rust rewrite (wait for that)

**Process**:
- Document as "Deferred - waiting for [reason]"
- Revisit in future phases
- Focus resources on higher-value migrations

## Success Criteria for Tier 2

A Tier 2 component migration is successful when:

1. ✅ **Builds with documented workflow**
   - Clear instructions for developers
   - Automated script available
   - CI/CD integration working

2. ✅ **Tests pass**
   - Existing tests still work
   - No regressions introduced
   - New tests added for Rust code

3. ✅ **Documentation complete**
   - Build process documented
   - FFI interfaces documented
   - Known limitations documented
   - Migration lessons captured

4. ✅ **Performance maintained**
   - No significant performance regression
   - Binary size acceptable
   - Build time reasonable

5. ✅ **Team can use it**
   - Developers can build and modify
   - Troubleshooting guide available
   - Support channels established

## Conclusion

Tier 2 migration is more complex than Tier 1 due to deep C++ integration. A hybrid build approach is realistic and practical for these components. Success requires:

- Clear documentation of build requirements
- Tooling to simplify hybrid builds
- Realistic expectations about Cargo limitations
- Incremental progress with frequent validation

The goal is not to force everything into pure Cargo, but to leverage Cargo's benefits (dependency management, tooling, ecosystem) while acknowledging Chromium's existing infrastructure.

**Recommendation**: Start with bluetooth BLE parser as a learning opportunity, document extensively, and refine the approach before scaling to more components.
